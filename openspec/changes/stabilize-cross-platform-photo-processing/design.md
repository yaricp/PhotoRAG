## Context

The packaged Python backend runs on all three desktop operating systems. Ollama is an external HTTP service and is stored as `mode=remote, model_provider=ollama`. `ChatOllama` is currently constructed without `num_ctx`, so PhotoRAG inherits the server's setting. On the test Mac, Ollama's app database held `context_length=262144`; its own log reported a 4,096-token hardware default, individual image prompts of about 4,044–8,408 input tokens, and a 29.8 GiB predicted load for Qwen3-VL on a 16 GiB machine. A model's advertised maximum context is not a suitable processing default.

The observer submits one `start_pipeline` coroutine for each new file on its own loop. Batch processing has a semaphore set to 20, but that semaphore does not cover observer submissions, folder-scanner tasks, or other processes. `asyncio.gather(..., return_exceptions=True)` lets later phases run after errors; `track_task` marks errors correctly, while the pipeline's final log and no-op tasks can look successful. The Processing page asks for only 50 recent task rows. At startup, `recover_interrupted_pipelines` deletes pending/running task rows and immediately reruns the affected photos.

The Folders page expects `Watcher.updated_at`, but the API's `Watcher` schema omits it. The pipeline-warning component reads configuration once on mount and has English-only text.

## Goals / Non-Goals

**Goals:** One cross-process entry path for photo runs; predictable Ollama memory pressure; truthful, persistent run/task outcomes; visible queue and complete photo-level history; user-controlled crash recovery; correct watcher timestamps and current localized model warnings. A normal user chooses a model, not a context token count.

**Non-Goals:** Bundling or changing Ollama's installation, changing its global context preference, changing the existing user-initiated model-pull workflow, automatically selecting/replacing a model for the user, guaranteeing that every model fits every computer, redesigning cloud-provider inference, or silently altering original photos to make an image fit a context window.

## Decisions

1. **Use one persistent run queue for all launch paths.** The observer, folder scans, user retries, agent tools and startup handling create or update a `pipeline_run` record; a single backend scheduler claims queued runs transactionally. This is preferable to adding another `asyncio.Semaphore`, which cannot cover the current separate event loops and worker processes. A photo cannot acquire two active full runs at once. On a constrained local-Ollama host, the initial admission limit is one photo run and one active Ollama inference request; the limit is kept separate from unrelated cloud/native work and can be raised only after platform measurements. Queue position and wait time are visible. Model calls that cannot finish within a bounded timeout fail visibly so the queue can progress.
2. **Negotiate context for the chosen model, not for a hard-coded name.** Query the configured Ollama server's `/api/show` for capabilities and native maximum context, and validate image support before accepting image roles. For photo-image roles, 16,384 tokens is the first candidate when the model and host can support it: the observed 8,408-token input still leaves response room. This is not a universal setting. A conservative host-capacity policy and the model's maximum bound the effective context; text and embedding roles get separately measured budgets. Reuse a stable effective context for the same model within a processing workload to avoid avoidable reloads. Send `num_ctx` in PhotoRAG's Ollama requests and display the selected value read-only; do not edit Ollama's app or process environment. When metadata or remote-host capacity is unknown, avoid claiming a guaranteed fit, use a bounded conservative attempt, and show the effective/unknown state.
3. **Never hide context or memory failures.** Image-token usage depends on the model and image, so file size alone is not an exact token preflight. On a context rejection, the existing tag/category candidate splitting may reduce the text portion; a larger context is attempted only if supported and within the capacity policy. A single image/description request that still cannot fit is failed with an actionable reason, without silent image truncation. Runner termination, HTTP 500, timeout and insufficient memory are bounded failures, not successful empty results or indefinite waits. Log photo/run/task ID, model, effective context, duration and error class without image contents or credentials.
4. **Represent work and dependencies explicitly.** Add a run ID to task attempts, preserving prior attempts and legacy photos through a migration. Run states are queued, running, completed, completed-with-errors, paused and interrupted. Task states include skipped with a reason. A failed description makes dependent translation/description embedding skipped, while independent successful tags or metadata remain valid. The run aggregate is successful only if all required tasks succeeded or were legitimately inapplicable; an unhandled failure or missing required output produces completed-with-errors. Retry records a new attempt for the failed task and reruns dependent skipped/stale tasks as needed, without clearing independent good results. A full rerun remains an explicit separate action.
5. **Separate active and completed views by run.** Backend pagination returns runs/photos, then all phase-0-to-4 task attempts for a selected run; a 50-task cutoff must not determine whether a completed photo is visible. The active tab shows queued/running/paused/interrupted work; the completed tab shows successful and completed-with-errors photos with actual output presence, error text and retry actions. A rerun of one photo does not erase or masquerade as the prior run's outcome.
6. **Make recovery opt-in.** On restart, existing active or queued work is marked interrupted/paused and remains visible; startup does not automatically enqueue it again. The user can resume selected runs or an explicitly selected set. New files arriving after startup can still be admitted normally. This replaces the current destructive recovery behavior and preserves diagnostic history.
7. **Correct status sources and wording.** Add `updated_at` to the watcher API, serialize a documented timezone-aware timestamp and handle absent/invalid legacy values. Label it as a status update, not a last-file-event time unless a separate event timestamp exists. Derive the warning banner from saved effective model configurations and current availability, refresh it after model saves/status changes, distinguish missing configuration from temporary unavailability, and localize all copy.

## Risks / Trade-offs

- **A single Ollama run lowers throughput on high-memory hosts** → Keep the admission policy configurable internally and raise it only after real multi-photo measurements; correctness and bounded memory are the release default.
- **Model metadata and file size cannot precisely predict runtime memory or image tokens** → Clamp to a conservative policy, catch explicit Ollama failures, and validate representative images on 8 GiB Windows and 16 GiB macOS plus Linux. Never silently truncate content.
- **Multiple functions use one Ollama model** → Reuse a stable context for pipeline calls to reduce reloading; disclose when a larger chat workload needs a different budget.
- **Persistent queue and retry migration affect existing databases** → Back up/migrate transactionally, preserve old photo content and task evidence, and provide rollback without deleting models or the Python environment.
- **Paused work may remain unfinished after a restart** → Show it prominently with a deliberate resume control; no automatic replay of old test photos.

## Migration Plan

Introduce additive run/attempt fields or tables, backfill one legacy run per existing photo from the latest task records without inventing missing history, and leave photo metadata, descriptions, tags, categories, model choices, Ollama downloads, and the existing venv intact. Convert old pending/running tasks to an interrupted state without launching them. Preserve the pre-migration database until the migration and startup verification pass. A rollback must not delete or reprocess photos.

## Open Questions

- Calibrate the automatic host-capacity policy and timeout on the actual Windows 8 GiB CPU test machine, macOS 16 GiB machine, and a Linux host before finalizing defaults. The specification fixes the externally observable behavior; these measurements choose the safe thresholds.
- Confirm whether an existing custom Ollama URL exposes model metadata; if it does not, show an unknown-capacity state and a bounded attempt rather than assuming local disk or memory information.
